Xcode Simulate Location Not Working? How to Fix It in the Simulator and on a Real iPhone

Xcode's Simulate Location usually breaks for one of four reasons: no debug session is attached, the GPX file is greyed out or missing, the GPX file uses tracks instead of waypoints, or the fake location lingers after you stop. Here is how to spot and fix each one, in the Simulator and on a real iPhone.

Quick answer: the four usual causes

  1. No debug session on a real iPhone. A debug session is the live link between Xcode's debugger and your running app. Xcode's Simulate Location menu works through that link. Fix: start the app with Run, debugger on, and pick the location again. To set a location without the debugger, see devicectl in Fix 4.
  2. The GPX file is greyed out or missing. GPX (GPS Exchange Format) is the XML file type Xcode reads for fake locations. Fix: add the file to your project, tick Allow Location Simulation in the scheme, and move other copies of Xcode out of the way.
  3. The GPX file has the wrong elements. Xcode plays waypoints (<wpt>), not tracks (<trk>). Fix: turn track points into waypoints and give each one a timestamp.
  4. The location lingers after you stop. Fix: restart the iPhone, or reconnect and choose Don't Simulate Location.

Menu, command and message names below come from Xcode 27.2 (27B52), in November 2026. Menus move between versions, so yours may differ slightly.

How Xcode location simulation works

In a simulator. In Xcode 27, simulators run inside Device Hub instead of the old Simulator app. Select the simulator and change its location in the Settings inspector. In Xcode 27.2 the location menu includes Custom Coordinates and Import GPX File. Older Xcode versions put the same controls under Features > Location in the Simulator app. From Terminal, xcrun simctl location booted set 51.5007,-0.1246 moves a running simulator and xcrun simctl location booted clear resets it.

While debugging. On a simulator or an iPhone, choose Debug > Simulate Location while your app runs under the debugger, or click the location arrow in the debug bar (the row of buttons at the top of Xcode's debug area). The menu lists built-in places plus the GPX files in your project.

Without the debugger. Xcode 27.2 also includes a Terminal command, xcrun devicectl device simulate location, that runs without a debug session. Fix 4 covers it, including what we couldn't test.

In the scheme. A scheme is Xcode's saved recipe for building and running a target. Open Product > Scheme > Edit Scheme, choose Run, then Options. Under the Core Location heading, tick Allow Location Simulation. Core Location is Apple's location framework. You can also set a Default Location that Xcode applies on every run.

In tests. Test plans have a Simulated Location setting, and UI tests can set XCUIDevice.shared.location. Apple notes that the test plan's location only reaches code in the test bundle. In UI tests your app runs as a separate process and doesn't get it, so set XCUIDevice.shared.location there instead.

Fix 1: Simulate Location greyed out or your GPX file missing

Apple's forums have threads on this for Xcode 9, 12.5.1 and 15.4. In the 15.4 thread, custom GPX files vanished from the menu, and Add GPX File to Workspace showed them all greyed out. Work through these steps in order.

  1. Check the scheme. Make sure Allow Location Simulation is ticked.
  2. Put the file in the project. Drag the .gpx file into the Project navigator and tick your app target when asked. You can also choose the file as the scheme's Default Location.
  3. Try a fresh project. If the file works in a new project, the old project is the problem. If not, your Mac is.
  4. Check the file type and the default app. macOS tags every file with a content type, called a UTI (Uniform Type Identifier). Xcode expects com.topografix.gpx, the type Xcode 27.2's own Info.plist declares for .gpx. Run: 
    mdls -name kMDItemContentType ~/Desktop/Route.gpx
    These are two separate problems with two separate fixes.
    • The type is wrong. Another app on your Mac has declared its own type for .gpx. Remove or update that app, move other copies of Xcode out of the way (next step), then run mdls again. Finder's Change All (below) only sets which app opens the file, so it won't fix this.
    • The type is right, but Finder shows another app's icon on the file. That was the case in the 15.4 thread. Reset which app opens .gpx files: select the file in Finder, choose File > Get Info, pick Xcode under Open with and click Change All.
    A correct type doesn't prove all is well: in the 15.4 thread the type was right and the menu was still broken.
  5. Move other copies of Xcode out of the way. Older and newer copies both count. This lists every Xcode on your Mac: 
    mdfind "kMDItemCFBundleIdentifier == 'com.apple.dt.Xcode'"
    In the 15.4 thread, old Xcode versions had come along when a developer migrated to a new Mac. Removing them and restarting Xcode 15.4 brought the GPX files back. In the 12.5.1 thread the extra copy was newer: one poster using Xcode 12 only had to move Xcode 13 to the Trash, without emptying it.
  6. Try a safe mode restart (unconfirmed). One developer said starting the Mac in safe mode, then restarting normally, fixed it. Nobody else confirmed it.
Reinstalling Xcode did not help the original poster in the 15.4 thread. Try the steps above before a long download.

Fix 2: The GPX loads, but the location doesn't move or jumps

Xcode plays waypoints. A waypoint is one <wpt> element with a latitude and longitude. Apple's older Simulator guide, quoted on Stack Overflow, says route (<rte>) and track (<trk>) tags are not supported. That is the trap, since GPX can also describe a path as a track. Xcode 27.2's GPX error messages still mention only waypoints.

Timestamps set the speed. Xcode works out the speed from the time between waypoints, and uses a fixed speed when there are no times. It moves in a straight line between points, so add waypoints wherever your path turns.

Going by its error messages, Xcode 27.2 treats the whole file as invalid if any waypoint:

  • is missing its latitude or longitude;
  • has a time with milliseconds (write 09:00:00Z, not 09:00:00.000Z);
  • has a time no later than the waypoint before it;
  • has more than one <time> element.

This small file follows all of those rules. It moves about 1.2 km across central London in 15 minutes, roughly walking pace.

<?xml version="1.0"?>
<gpx version="1.1" creator="Xcode">
    <wpt lat="51.5007" lon="-0.1246">
        <name>Start</name>
        <time>2026-01-01T09:00:00Z</time>
    </wpt>
    <wpt lat="51.5014" lon="-0.1419">
        <name>End</name>
        <time>2026-01-01T09:15:00Z</time>
    </wpt>
</gpx>

Save it as a .gpx file, add it to your project, and pick it from Debug > Simulate Location. For one fixed spot, use a single waypoint with no time.

Converting a track you already have

Delete the <trk> and <trkseg> wrapper tags, then rename every trkpt to wpt. One Stack Overflow answer suggests the free GPSBabel tool instead:

gpsbabel -i gpx -f track.gpx -x transform,wpt=trk,del -o gpx -F converted.gpx

Then check that every waypoint kept its <time>, without milliseconds.

Fix 3: It works in the Simulator but not on the iPhone

A real iPhone needs three things.

  1. A running debug session. Start the app with Product > Run. Apple notes that turning off Debug executable in the scheme's Info tab runs the app without the debugger. Leave it on, because Xcode's Simulate Location menu works through the debug session.
  2. Developer Mode. This iOS switch lets you run apps from Xcode on the phone. Turn it on in Settings > Privacy & Security > Developer Mode and tap Restart. After the restart, swipe up, tap Enable and enter your passcode. Apple says the switch only appears once you start pairing with a Mac, or if the phone was paired before. If it's missing, read Developer Mode not showing on iPhone.
  3. A paired, trusted phone. In Xcode 27 you pair devices in Device Hub, then tap Trust on the phone. Apple says wireless pairing needs iOS or iPadOS 27 or later. On older versions, pair over a cable first. After that you can unplug and run over Wi-Fi, with IPv6 turned on, on the same network as your Mac.

Then pick a location from the debug bar.

Fix 4: It stopped when I stopped debugging (or it won't stop)

If the fake location vanished when you pressed Stop, nothing is broken. A location set from the debug bar belongs to the debug session, and ending the session can hand location back to the phone's real sensors. One developer on iOS 17 reported the phone returning to real GPS after disconnecting from Xcode.

Keeping a location without the debugger: devicectl

If you want the location to stay after you stop, try devicectl, the device command-line tool that comes with Xcode. In Xcode 27.2 it has a simulate location command with coordinate, route, scenario, list and clear subcommands. Its built-in help says a coordinate simulation continues until you clear it, and doesn't mention the debugger. For --device, pass your phone's name or its UDID.

xcrun devicectl device simulate location coordinate --device "My iPhone" --latitude 51.5007 --longitude -0.1246
xcrun devicectl device simulate location clear --device "My iPhone"

We haven't tested devicectl on a physical iPhone. Before you rely on it, check that the location holds after you quit Xcode and unplug. Run xcrun devicectl help device simulate location to see the options your Xcode version has. It still needs a Mac with Xcode and a terminal.

When the location won't go away

Older reports show the opposite problem. In a 2014 Stack Overflow question, an unplugged iPhone stayed at the simulated spot in Google Maps. In another from the same month, a phone stayed stuck in New York. What to try:

  1. Restart the iPhone. That's what cleared the New York phone.
  2. Reconnect, run the app, open the location menu in the debug bar and choose Don't Simulate Location. Then stop. This was the top answer to the Google Maps question.
  3. As a last resort, use Settings > General > Transfer or Reset iPhone > Reset > Reset Location & Privacy. Apple says this returns location and privacy settings to their defaults without erasing your content.

To stop the next run applying the spot again, set the scheme's Default Location to None, or untick Allow Location Simulation if you don't need it. On their own, these don't free a phone that's already stuck. Both 2014 askers had tried them, and the New York phone only came free after a restart.

For more ways back, see how to get your real location back.

Fix 5: CLLocationManager never delivers updates

Sometimes the simulation seems set up but your code hears nothing. CLLocationManager is the Core Location class your app uses to ask for location. Check four things.

  • An error with kCLErrorDomain Code=0. Code 0 is CLError.Code.locationUnknown, which Apple describes as the location manager being unable to get a location right now. In a simulator, the top Stack Overflow answer on this error traces it to Allow Location Simulation being ticked with no Default Location set. Make sure a location is actually set: pick one in the simulator's Settings inspector in Device Hub, or choose a Default Location in the scheme.
  • The usage string. Info.plist, your app's settings file, must contain NSLocationWhenInUseUsageDescription: a sentence explaining why you need location. Apple says the key is required when you call requestWhenInUseAuthorization(), and its text appears in the prompt.
  • The permission request. Call requestWhenInUseAuthorization() or requestAlwaysAuthorization() before expecting any location, with the app in the foreground. Once permission is decided, the call does nothing, so an old "Don't Allow" sticks. Change it in Settings > Privacy & Security > Location Services. On a simulator, reset just your app's location permission from Terminal, using your app's bundle ID: 
    xcrun simctl privacy booted reset location com.example.app
    As a last resort, shut the simulator down and choose Device > Reset Content and Settings in Device Hub, which erases the whole simulator.
  • Reduced accuracy. If Precise Location is off for your app, it only gets an approximate location. Apple says desiredAccuracy then has no effect, and the app can't use region monitoring or beacon ranging (measuring the distance to nearby Bluetooth beacons). Region monitoring is Core Location's geofencing, so geofence tests won't work while Precise Location is off. Check accuracyAuthorization. See precise vs approximate location and how to test geofencing without driving.

When Xcode isn't enough

Xcode is the right free tool while you debug, and its fake location even reaches other apps (one of the 2014 questions saw it in Google Maps). The debugger's Simulate Location ends with the debug session, and devicectl (Fix 4) needs a Mac with Xcode and a terminal. Sometimes you need a location on a real iPhone without those: from a Windows or Linux computer, for a tester who doesn't use Xcode, or with no computer nearby. For automated tests and CI (continuous integration: automated builds that run your tests on a server), stick with Xcode's own tools.

Free option: pymobiledevice3

pymobiledevice3 is an open-source Python tool (GPL 3.0) for working with iPhones from macOS, Windows or Linux. Its location commands use DVT, the developer-tools service Xcode uses, and need Developer Mode. On iOS 17 and later:

pymobiledevice3 developer dvt simulate-location set -- 51.5007 -0.1246
pymobiledevice3 developer dvt simulate-location play route.gpx
pymobiledevice3 developer dvt simulate-location clear

On iOS 17 and later, set keeps its session open until you press Ctrl+C, so the computer stays connected. You need a terminal, but no Xcode and no debugger.

Unlike Xcode, pymobiledevice3's play reads only track points (<trkpt>) and ignores waypoints, so keep your original track file for it. A waypoint-only file, like the sample in Fix 2, gives no movement. It also jumps from point to point without filling in the gaps, so use a dense track.

Wander: one location for the whole iPhone

Wander changes the location your iPhone reports at the system level, over Apple's own developer tunnel. Everything on the phone reads it: maps, weather and your own build. Our iPhone page lists geo-feature testing for developers as a use. You can run it two ways.

  • The iPhone app. A one-time setup on a Mac or Windows PC installs it with a free Apple ID (the Windows installer is in beta and needs Apple's free Apple Devices app). You turn on Developer Mode and add LocalDevVPN, a free tunnel app from the App Store. After that, you don't need the computer. The download page has every step.
  • Wander Desktop for Mac. It drives a tethered iPhone (one connected to the Mac by cable or on the same Wi-Fi) with nothing installed on the phone, on Apple Silicon and Intel Macs. It is an unsigned build: it isn't signed with a paid code-signing certificate, so macOS may warn you the first time you open it. It also asks for your Mac password once because it needs admin rights to open the secure tunnel to your iPhone. Plug the phone in (or join the same Wi-Fi), click Connect Device, then teleport or run a route. On a PC, see changing iPhone location from Windows.

For testing: search by coordinates is free, multi-stop routes snap to roads at a realistic speed, GPX import lets you bring your own GPX files, and the Panic Button snaps you back to real GPS. Multi-stop routes and GPX import need Pro; the free plan includes 1 teleport a day and 3 two-stop routes a month (see pricing and features). The iPhone app is open source (GNU AGPL v3), as is the desktop app (GNU GPL v3); see our security page.

Developer-tunnel locations count as simulated. iOS marks any location set through Apple's developer tunnel as software-simulated. Core Location reports it as isSimulatedBySoftware in a location's sourceInformation, and Apple's docs give GPX playback in the Xcode debugger as an example. An app that reads that flag treats Xcode, pymobiledevice3 and Wander's developer-tunnel mode (the one described above) the same way. If your app rejects simulated fixes outside testing, as Apple suggests apps may, test that path on purpose with Xcode or a developer-tunnel tool.

Some apps' terms forbid changing your location. If you use a location tool with someone else's app, following its rules is up to you.
